01

Introducción

Modelo empresarial

Grupo Helse S.A.S. es un grupo empresarial colombiano dedicado a la operación logística y de distribución en el sector salud. Cuenta con una línea de operación logística dedicada a la comercialización, el almacenaje y la entrega nacional de productos farmacéuticos, fórmulas nutricionales, dispositivos médicos e insumos. Dentro de su operación se desarrollan diferentes actividades relacionadas con la gestión de clientes, la recepción y generación de pedidos y el posterior proceso de envío de los productos. Debido a la cantidad de información que se genera en estas actividades, es importante contar con una estructura que permita organizar los datos de manera adecuada y representar claramente la relación entre los diferentes procesos.

El recorrido se desarrolla de manera progresiva. Primero, el modelo entidad–relación (E–R) identifica las entidades, sus atributos y las relaciones del negocio. Después, el modelo relacional transforma esos elementos en tablas conectadas mediante claves primarias y foráneas. Antes de implementar la estructura en SQL, se incorpora una verificación lógica necesaria: la normalización. Esta revisión comprueba que cada dato ocupe el lugar que le corresponde, reduce repeticiones y aclara las dependencias entre clientes, pedidos, productos y envíos. Así, la implementación física no parte de un esquema provisional, sino de uno previamente revisado y preparado para crecer de forma ordenada (Köhler & Link, 2018).

02

Construcción de la base de datos

El diseño avanza desde la comprensión del negocio hasta su implementación en un sistema gestor.

La construcción de una base de datos se entiende aquí como un flujo de cuatro pasos. Cada uno responde una pregunta: ¿qué información necesita el negocio?, ¿cómo se organiza en tablas?, ¿la estructura está libre de redundancias y dependencias inadecuadas?, ¿cómo se implementará técnicamente? La normalización se integra como control de calidad del diseño lógico: valida el esquema antes de convertirlo en instrucciones SQL (Ling et al., 1981; Köhler & Link, 2018).

FASE 1 · CONCEPTUAL

Modelo entidad–relación

Primero se interpretan las reglas del negocio y se representan las entidades, sus atributos y las relaciones que las conectan, sin decidir todavía tipos de datos o características de un programa específico.

01CLIENTE — GENERA — PEDIDO

Un cliente puede generar varios pedidos y cada pedido pertenece a un solo cliente.

02PEDIDO — CONTIENE — PRODUCTO

Un pedido puede contener varios productos y un producto puede estar incluido en varios pedidos. El atributo Cantidad, unido a esta relación, registra cuántas unidades de un producto solicita el cliente en ese pedido específico.

03PEDIDO — ALISTAMIENTO — ENVÍO

Cada pedido se asocia con un envío y cada envío corresponde a un solo pedido.

Cantidad e Inventario no significan lo mismo

Cantidad pertenece a la relación CONTIENE y responde: “¿cuántas unidades de este producto solicita el cliente en este pedido?”. Inventario pertenece a la entidad PRODUCTO y responde: “¿cuántas unidades de este producto tiene disponibles Grupo Helse?”. Se representan por separado porque la cantidad solicitada cambia en cada pedido, mientras que el inventario describe la disponibilidad del producto.

Cadena lógica del modelo

Un cliente genera un pedido. El pedido contiene uno o varios productos y, para cada producto, el atributo Cantidad registra las unidades solicitadas. Cada producto conserva además su atributo Inventario, que indica las unidades disponibles en Grupo Helse. Esta separación permite comparar lo solicitado con lo disponible. Finalmente, el pedido pasa por el proceso de alistamiento y se asocia con el envío de cada entrega.

FASE 2 · LÓGICA

Del modelo E–R al modelo relacional

Las entidades se convierten en tablas, los atributos en columnas y las claves identifican o conectan registros. La cardinalidad guía la transformación de cada relación.

De la cardinalidad a las tablas

Presiona cada transformación para conocer cómo se representa en el modelo relacional.

1:M
CLIENTE — PEDIDOUno a muchos
+

CLIENTE y PEDIDO se convierten en tablas independientes. Como un cliente puede tener varios pedidos, la identificación del cliente se incorpora en PEDIDO. Así, cada pedido puede asociarse con un solo cliente, mientras un cliente puede aparecer en diferentes pedidos.

M:N
PEDIDO — PRODUCTOMuchos a muchos
+

Una relación muchos a muchos genera una tabla intermedia llamada PRODUCTOS_PEDIDO. Esta tabla reúne la identificación del pedido y la del producto. También almacena Cantidad, porque este dato depende de la combinación entre un pedido y un producto.

1:1
PEDIDO — ENVÍOUno a uno
+

PEDIDO y ENVÍO se mantienen como tablas independientes. La remisión del pedido se registra en ENVÍO para conservar la correspondencia entre ambos. Esta referencia debe ser única para garantizar que cada pedido se asocie con un solo envío.

1:M
ENVÍO — MÉTODO_ENVÍOAtributo multivaluado
+

Como un envío puede registrar varios métodos, el atributo método de envío se transforma en una tabla separada. Cada registro de METODO_ENVIO queda asociado con un envío, lo que permite almacenar varios métodos sin repetir los demás datos del envío.

Cadena lógica del modelo relacional

CLIENTE se relaciona con PEDIDO; PEDIDO se conecta con PRODUCTOS mediante PRODUCTOS_PEDIDO; PEDIDO se asocia con ENVÍO; y ENVÍO se relaciona con METODO_ENVIO.

PASO 3 · VERIFICACIÓN LÓGICA

Normalización de la base de datos

Antes de escribir SQL, se comprueba que cada dato sea atómico, dependa de la clave correcta y se almacene en la tabla que describe. Este control reduce anomalías de inserción, actualización y eliminación.

1FN

Un dato por celda

Elimina grupos repetidos y deja cada producto solicitado en un registro independiente.

2FN

Dependencia de la clave completa

En PRODUCTOS_PEDIDO, la cantidad depende de la combinación entre pedido y producto; los datos propios del producto permanecen en PRODUCTO.

3FN

Sin dependencias transitivas

El nombre y la ciudad del cliente se guardan en CLIENTE; PEDIDO conserva únicamente su identificador como clave foránea.

La normalización no interrumpe el recorrido: lo valida

El modelo relacional propone las tablas; la normalización comprueba su estructura; y SQL implementa el resultado verificado. Las dependencias funcionales —por ejemplo, id_producto → nombre_producto e id_cliente → nombre_cliente, ciudad— permiten decidir en qué tabla debe quedar cada atributo (Ling et al., 1981).

De la estructura a la información

Consultas SQL aplicadas

Una vez validada la estructura, el siguiente paso fue comprobar si la base respondía preguntas útiles para la operación de Grupo Helse.

¿Qué productos contiene cada remisión, en qué cantidades y a qué cliente pertenece?

Reconstruir el detalle de un pedido permite identificar al cliente, los productos solicitados y sus cantidades a partir del número de remisión.

Tablas participantes: cliente → pedido → productos_pedido → productos

La consulta

Los JOIN reúnen información distribuida en tablas normalizadas. ORDER BY organiza el detalle por remisión y nombre del producto.

USE final;

SELECT
    pedido.Nro_remision,
    cliente.Nom_cliente,
    productos.Nom_producto,
    productos_pedido.Cantidad
FROM pedido
JOIN cliente
    ON pedido.Idcliente = cliente.idCLIENTE
JOIN productos_pedido
    ON pedido.Nro_remision = productos_pedido.Nro_remision
JOIN productos
    ON productos_pedido.Id_producto = productos.Id_producto
ORDER BY pedido.Nro_remision, productos.Nom_producto;

Cómo leer el resultado

Cada fila vincula una remisión con su cliente, un producto y la cantidad solicitada. Una remisión con varios productos aparece en varias filas.

Alcance de la respuesta

El resultado describe las líneas de pedido registradas; no demuestra por sí solo que los productos hayan sido despachados o entregados.

¿Qué productos solicitados pueden cubrirse actualmente con el inventario disponible y cuáles presentan insuficiencia?

Comparar la cantidad de cada línea de pedido con el inventario actualmente registrado ayuda a identificar necesidades de abastecimiento.

Tablas participantes: productos_pedido → productos

La consulta

CASE compara cantidades y clasifica cada línea como inventario suficiente o insuficiente. AS asigna nombres claros a las columnas del resultado.

USE final;

SELECT
    productos_pedido.Nro_remision,
    productos.Nom_producto,
    productos_pedido.Cantidad AS Cantidad_solicitada,
    productos.Inventario AS Inventario_actual,
    CASE
        WHEN productos.Inventario >= productos_pedido.Cantidad
        THEN 'Inventario suficiente'
        ELSE 'Inventario insuficiente'
    END AS Estado_inventario
FROM productos_pedido
JOIN productos
    ON productos_pedido.Id_producto = productos.Id_producto
ORDER BY productos_pedido.Nro_remision, productos.Nom_producto;
Descargar Query 2.sql ↓
Cómo leer el resultado

Cantidad_solicitada se contrasta con Inventario_actual. Si el inventario es mayor o igual a la cantidad de esa línea, se muestra «Inventario suficiente»; en caso contrario, «Inventario insuficiente».

Alcance de la respuesta

La base no tiene un historial de inventario por fecha: no permite saber si había existencias al realizar el pedido. La comparación es individual por línea y no descuenta ni acumula la demanda de otras remisiones; no garantiza cubrirlas todas simultáneamente.

Evidencia en MySQL Workbench
¿Qué remisiones destinan una mayor proporción de su valor al costo acumulado de sus envíos?

Identificar remisiones cuyo transporte tiene un peso relativo alto permite orientar la revisión de los costos logísticos.

Tablas participantes: pedido → envio

La consulta

Como PEDIDO → ENVIO es 1:N, SUM acumula los costos de todos los envíos por remisión. GROUP BY agrupa, ROUND redondea a dos decimales y ORDER BY DESC muestra primero los porcentajes mayores.

USE final;

SELECT
    pedido.Nro_remision,
    pedido.Valor_remision,
    SUM(envio.Costo_envio) AS Costo_total_envios,
    ROUND(
        (SUM(envio.Costo_envio) / pedido.Valor_remision) * 100,
        2
    ) AS Porcentaje_envio
FROM pedido
JOIN envio
    ON pedido.Nro_remision = envio.Nro_remision
GROUP BY
    pedido.Nro_remision,
    pedido.Valor_remision
ORDER BY Porcentaje_envio DESC;
Descargar Query 3.sql ↓
Cómo leer el resultado

Porcentaje_envio = (costo total de los envíos ÷ valor de la remisión) × 100. Un porcentaje mayor indica que el transporte representa una proporción mayor del valor de esa remisión.

Alcance de la respuesta

Este porcentaje no representa rentabilidad, margen ni utilidad neta: faltan los demás costos de operación. El JOIN incluye remisiones con envíos registrados; si el valor de una remisión es cero o nulo, el porcentaje no es interpretable.

03

Análisis del modelo

Hallazgos de la operación y verificación

Selecciona cada hallazgo para explorar el diseño del modelo y los resultados de las tres consultas SQL. Los análisis 06, 07 y 08 interpretan las evidencias de MySQL Workbench.

01

La remisión permite seguir cada pedido desde el cliente hasta el envío.

+

Cada pedido recibe un número de remisión único. En la tabla PEDIDO, este número funciona como clave primaria: es el dato que identifica exclusivamente cada pedido y evita confundirlo con otro.

El mismo número aparece en ENVIO y PRODUCTOS_PEDIDO como clave foránea. Esto significa que se utiliza en esas tablas como una referencia al pedido original. Además, PEDIDO conserva la identificación del cliente. Por esta razón, al consultar una remisión se puede conocer qué cliente generó el pedido, qué productos solicitó, cuántas unidades pidió y cuál es la información de su envío.

02

El modelo permite conocer qué productos se venden, en qué cantidades y a qué clientes.

+

La tabla PRODUCTOS_PEDIDO funciona como un punto de conexión entre los pedidos y los productos. Cada registro indica qué producto fue incluido en un pedido y cuántas unidades fueron solicitadas.

Por su parte, PEDIDO permite conocer qué cliente realizó la compra. Al relacionar esta información, la empresa podrá identificar qué productos se venden, en qué cantidades, cuáles se solicitan con mayor frecuencia y qué pedidos ha realizado cada cliente.

03

El modelo permite comparar las unidades disponibles con las cantidades solicitadas.

+

La tabla PRODUCTO contiene el inventario, es decir, la cantidad disponible de cada producto. La tabla PRODUCTOS_PEDIDO, a su vez, registra la cantidad solicitada dentro de cada pedido.

Al comparar ambas cantidades, la empresa puede determinar si dispone de suficientes unidades para atender el pedido. Esta información ayuda a controlar la disponibilidad de los productos y a reducir el riesgo de aceptar pedidos que no puedan atenderse.

04

El modelo permite comparar el valor de la venta con el costo de su envío.

+

PEDIDO almacena el valor de la remisión, correspondiente al valor registrado para la venta, mientras que ENVIO almacena el costo de entregarla. Como ambas tablas se conectan mediante la remisión, se pueden comparar directamente estos valores.

La diferencia permite calcular un margen asociado al transporte y conocer cuánto queda del valor de la venta después de descontar únicamente el costo de envío. Este resultado no representa la rentabilidad total, porque el modelo no incluye todos los costos empresariales; sin embargo, sí permite comparar las ventas con los costos de envío e identificar qué proporción de cada pedido se destina al transporte.

05

La normalización reduce repeticiones y facilita mantener datos coherentes.

+

La primera forma normal asegura valores atómicos; la segunda separa los atributos que no dependen de toda la clave compuesta; y la tercera evita que datos como el nombre o la ciudad del cliente se repitan en cada pedido.

En consecuencia, un cambio se realiza principalmente en la tabla correspondiente y se propaga mediante las relaciones. Esto disminuye inconsistencias, hace explícitas las dependencias y prepara un esquema más estable para la implementación en SQL (Köhler & Link, 2018).

06

SQL · Los JOIN vinculan cada remisión con su cliente, sus productos y las cantidades solicitadas.

+

En la captura, la remisión 678 corresponde a DISTRIBUCIONES PHARMASER LIMITADA y contiene 52 unidades de ENSURE ADVANCE LIQUIDO VAINILLA RPB. La remisión 679 vincula el mismo producto con TADA INVERSIONES SAS y 26 unidades. Los JOIN permiten leer juntos el cliente, la remisión y el detalle del producto.

La consulta relaciona cliente, pedido, productos_pedido y productos. Cada fila describe una línea registrada; por sí sola no demuestra despacho ni entrega.

07

SQL · La suficiencia por línea no garantiza cubrir la demanda acumulada.

+

Todas las filas completas visibles están clasificadas como «Inventario suficiente». Por ejemplo, la remisión 678 solicita 52 unidades de ENSURE ADVANCE LIQUIDO VAINILLA RPB frente a 200 registradas. Sin embargo, al sumar solo las cuatro líneas visibles de ese producto (remisiones 678, 679, 5242 y 5252), obtenemos 52 + 26 + 130 + 65 = 273 unidades. Si debieran atenderse simultáneamente con esas 200 unidades, faltarían 73. Esta suma es una lectura de las filas de la captura, no una columna calculada por la consulta. Confirma por qué evaluar cada línea no equivale a cubrir la demanda acumulada.

La consulta compara cada línea con el inventario actual, sin reservar existencias ni acumular otros pedidos. Tampoco permite reconstruir el inventario disponible en una fecha pasada.

08

SQL · El costo acumulado de los envíos permite comparar su peso sobre cada remisión.

+

La remisión 8992 aparece primero: valor de 1.924.000, costo total de envíos de 400.000 y proporción de 20,79 %. Le siguen la 8991 con 18,67 % y la 5252 con 17,09 %. La remisión 5250 tiene un costo de envíos mayor, 1.500.000, pero una proporción menor, 14,20 %, porque su valor es 10.560.000. Son proporciones logísticas, no márgenes de ganancia.

La relación PEDIDO 1:N ENVIO exige sumar los costos de todos los envíos de cada remisión antes de calcular el porcentaje. El indicador orienta la revisión logística; no calcula rentabilidad.

04

Conclusión

El proyecto representa de manera continua una parte del proceso logístico de Grupo Helse S.A.S.: el modelo entidad–relación interpreta las reglas del negocio, el modelo relacional las convierte en tablas y la normalización verifica que cada atributo dependa de la clave adecuada y permanezca en la entidad que describe. La primera, segunda y tercera forma normal reducen repeticiones y previenen inconsistencias sin alterar las relaciones necesarias para seguir clientes, pedidos, productos y envíos. Con esta revisión, la implementación SQL deja de ser un salto técnico y se convierte en la consecuencia natural de un diseño conceptualizado, estructurado y validado. Para una microempresa, este flujo facilita el mantenimiento de la información y permite que la base de datos crezca de forma ordenada.

La Unidad 4 completa este recorrido con una implementación reproducible en MySQL. La validación mediante Reverse Engineer permitió contrastar el diseño y precisar las relaciones PEDIDO 1:N ENVIO y METODO_ENVIO 1:N ENVIO. El archivo SQL conserva la estructura, las claves, las relaciones y los datos necesarios para reconstruir el ejercicio y repetir las consultas.

Las tres consultas convierten esa estructura en información útil: vinculan clientes con pedidos y productos, comparan las cantidades solicitadas con el inventario registrado y calculan el peso del transporte sobre cada remisión. Las evidencias también delimitan las conclusiones: una línea con inventario suficiente no garantiza atender toda la demanda simultáneamente, y el porcentaje de envío no representa rentabilidad. Así, el proyecto integra diseño, normalización, implementación y análisis para apoyar decisiones logísticas sustentadas en los datos disponibles.
